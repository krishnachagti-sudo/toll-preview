How it decides

Dates: proof, not guesses

A date like 13/03/2026 can only be DD/MM; 03/13/2026 can only be MM/DD. Each column is read by the values that prove its order. A column holding both is mixed: each provable row is read its own way, and rows like 03/04/2026, which read either way, are listed and left as written unless your recipe names the order. Two-digit years follow Excel's own rule: 00 to 29 are 2000 to 2029, 30 to 99 are 1930 to 1999.

Leading zeros: only to a known width

ZIP codes go back to 5 digits (ZIP+4 to 9), because that is what a ZIP code is. Codes such as account numbers are kept as text, so the zeros that are still there stay. A code is padded to a width only when your recipe states it: when most values share a width and the rest are shorter, the scan shows that width for you to confirm, but never applies it by itself.

Encoding and garbled accents

A byte order mark is read first, then the bytes are checked as UTF-8; a file that is not valid UTF-8 is read as Windows-1252. Text that was UTF-8 read the wrong way (CafÃ© for Café) is turned back, value by value, only where that gives valid UTF-8. The fixed file is UTF-8 with a BOM by default, which Excel reads correctly.

Please read

  • Files are processed in memory and not kept. A recipe holds settings only (column headings and rules), never the values in your file.
  • A date whose day and month are both 12 or below cannot be settled from the value alone. It is read by its column's proven order or by your recipe; otherwise it is listed and left as written.
  • Digits Excel already cut to 15, and zeros already stripped from codes with no known width, are not in the file any more. They are flagged, never invented.
  • Check the change report before importing the file into an accounting or payroll system.
