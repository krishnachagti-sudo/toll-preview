How to read a DMARC report

Each <record> is one sending IP: <count> is the number of messages, and <policy_evaluated> gives the receiver's aligned DKIM and SPF results and its action (RFC 9990 sections 3.1.1.8 and 3.1.1.9); DMARC passed if either aligned result is pass. In the sample below, 57 messages from Amazon SES (54.240.8.17) failed because dKIM passed for d=amazonses.com and SPF passed for us-east-1.amazonses.com, but neither is example.com, so neither aligns.

The parts of a report

From RFC 9990 section 3.1.1 (the XML schema is its Appendix A); RFC 7489 Appendix C has the same parts.
ElementHoldsWhat it tells youRFC 9990
report_metadataorg_name, email, report_id, date_range (begin and end in seconds since 1970, UTC)Who sent the report and which day it covers.3.1.1.3
policy_publisheddomain, p, sp, np, adkim, aspf, testing, discovery_method (RFC 7489 also pct)The DMARC record the receiver found for your domain.3.1.1.5
record/rowsource_ip, countOne sending IP and how many messages it sent for this combination of results.3.1.1.8
row/policy_evaluateddisposition (none, quarantine, reject; RFC 9990 adds pass), dkim, spf, reasonThe DMARC verdict: aligned DKIM and aligned SPF, and what the receiver did. DMARC passes if either is pass.3.1.1.9
record/identifiersheader_from, envelope_from, envelope_toThe From: domain, the bounce (MAIL FROM) domain and, from some reporters, the recipient's domain.3.1.1.10
auth_results/dkimdomain (d=), selector (s=), resultEvery DKIM signature checked, with its raw result before alignment.3.1.1.12
auth_results/spfdomain, scope (mfrom), resultThe raw SPF result for the domain that was checked.3.1.1.13
policy_evaluated/reasontype, commentWhy the receiver applied a different action than your policy asked.3.1.6

Aligned results and raw results

The most common confusion: policy_evaluated holds the results as they relate to DMARC, so dkim and spf there are pass only when they passed for a domain aligned with your From: domain. auth_results holds the raw DKIM and SPF results, uninterpreted. Microsoft's guide puts it the same way: an SPF auth pass with an SPF aligned fail means the sender is authorized but not set up for DMARC.

typeMeaning

Sources

  • RFC 9990: DMARC Aggregate Reporting (May 2026), read November 8, 2026
  • RFC 7489: DMARC (2015, now obsolete), Appendix C schema, read November 8, 2026
  • Microsoft Learn: Set up DMARC (updated July 17, 2026), read November 8, 2026

Source names are inferred from published provider data (each provider's SPF ranges, the signing and bounce domains its own documentation names, and the AWS and Google Cloud range lists), read on the dates shown, with the evidence listed for every name. Shared infrastructure can carry several companies' mail, so check before you change DNS. Reports you upload are read in memory and not kept.

Steps

  1. Check who sent it and for which day. report_metadata gives the reporter (org_name, email) and date_range in seconds since 1970, UTC.
  2. Check the policy it saw. policy_published is your DMARC record as the receiver found it: p, sp, np and the alignment modes.
  3. Read each record. row/source_ip is the sending IP and count the number of messages; policy_evaluated gives aligned DKIM and SPF and the action taken.
  4. Find why a record failed. If both aligned results are fail, auth_results shows which domains DKIM and SPF passed or failed for; a pass for another domain means a missing alignment, not a forgery.
  5. Name the source. Match the IP against the ranges your senders publish, or drop the file in the analyzer, which names it with the evidence.
